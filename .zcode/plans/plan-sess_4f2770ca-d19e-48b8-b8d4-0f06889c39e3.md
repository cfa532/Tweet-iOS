# Port the Android client to owner-only writes

## Context

The backend (release `tweet1` 1486, debug `twbe` 1733) now routes comments, engagement (likes/bookmarks/retweet counts), and messages through the acting user's own root node with a Leither session, falling back to old wire forms on old nodes via `health` capability flags (`userSessions`, `commentDelegation`, `engagementDelegation`, `messageDelegation`). iOS and TweetWeb are ported; Android is the last client, currently broken on the new backend for comments/likes/bookmarks/retweet-counts/messages (reads and self-writes still work). This port mirrors the other two clients exactly.

Android's structure is favorable: 100% Kotlin, all entry calls built in one file (`HproseInstance.kt`), a `health` capability probe already exists (`storageCapabilities`, HproseInstance.kt:316–393) reading `storageFormats` with 60s TTL — we extend it rather than invent anything.

## Work — all in a new branch `owner-only-writes` from `main`

### 1. Session plumbing — new `UserSession.kt` (in `datamodel/` or `network/`)

Mirror of TweetWeb's `src/utils/userSession.ts` and iOS `OwnerSession.swift`:
- `leitherLogin(client, username, password)` → hprose `Login` RPC (already on the RPC interface? — HproseService.kt has `login(ppt)`; verify the Leither-level `Login(u,p)` byname method is callable through the client; add it to the service interface if needed, like iOS/TweetWeb call `Login`/`LoginWithPPT` directly on the node) → `{Sid, Uid}`.
- Per `(accountId, nodeUrl)` in-memory session cache with 45-min freshness + `discard`; "Session invalid" reply detection; one re-sign-in retry.
- Guest credential storage in `PreferenceHelper` (username/password for the signed-in account, cleared on logout). Note in code: iOS uses Keychain; Android uses encrypted prefs if available, else plain SharedPreferences with a comment (match existing app behavior — it already stores password in Room cache, so prefs is no worse).
- Leither `Register(name, pass, "")` helper for registration.

### 2. Capability probe — extend `storageCapabilities` (HproseInstance.kt:316–393)

Parse `userSessions`, `commentDelegation`, `engagementDelegation`, `messageDelegation` from the same cached health reply (additive booleans, default false → old wire forms).

### 3. Write choke point — `runWrite(entry, params, client)` in HproseInstance

Mirrors TweetWeb's `runWrite`: maps entry→owning account (`update_tweet`/`toggle_tweet_privacy`/`toggle_pinned_tweet`/`delete_comment`/`toggle_favorite`/`retweet_added`/`retweet_removed` → `appuserid`; `delete_tweet`/`toggle_following`/`toggle_bookmark`/`block_user`/`remove_blacklisted_relationship`/`set_user_avatar`/`delete_account`/`message_outgoing`/`message_fetch`/`share_file` → `userid`; `add_tweet`/`add_comment` → authorId in JSON payload; `set_author_core_data` → mid in `user` JSON), attaches `usersid` when the device holds the credential, retries once on "Session invalid". Route the existing call sites through it.

### 4. Comment flows — capability-gated reroute (HproseInstance.kt:5042, 4247)

`uploadComment` and `delComment`: probe `commentDelegation` on the parent author's node; if true, send to the **acting user's** `requireWritableClient(appUser)` instead of the parent author's, params unchanged plus `requestid` (below). `delComment` param is `userid` there — align to `appuserid` like iOS if the new backend expects it (check SERVER_API.md — delete_comment takes `appuserid`).

### 5. Engagement flows — same gate (HproseInstance.kt:4508, 4560, 4111)

`toggleFavorite`/`toggleBookmark`/`updateRetweetCount`: probe `engagementDelegation` on the storage author's node; if true, reroute to appUser's writable client.

### 6. Messages — drop the direct recipient write (HproseInstance.kt:1155–1370)

`sendMessage`: probe `messageDelegation` on the sender's root; if true, skip step 2 entirely (`message_outgoing` now delivers both halves); raise step-1 timeout to 30s. Old nodes keep both steps. `fetchMessages`/`checkNewMessages` already target appUser's root — no change.

### 7. requestid idempotency (HproseInstance.kt:4166 uploadTweet, 5042 uploadComment)

Generate a UUID per composition (in the ViewModels or at the HproseInstance boundary — at the boundary is simpler: `uploadTweet`/`uploadComment` accept an optional `requestId`, callers in `TweetWorker`/`TweetViewModel` generate and retain per operation; simplest v1: generate inside uploadTweet/uploadComment when absent, quote path derives `<id>-quote`). Retry-safe on the new backend; ignored by old backends.

### 8. Login/register flows (HproseInstance.kt:1627 login, 2014 registerUser)

- `login`: when the account's root advertises `userSessions`, Leither-sign-in on the root first, then call `login` with `username`+`password`+`usersid` (password retained for legacy binding); store the guest credential on success.
- `registerUser`: on a `userSessions` node, Leither `Register`+`Login` first, then `register` with `usersid` and **no password in the user blob**; remember session for the auto-follow that follows (it goes through `toggle_following` → runWrite).

### 9. Owner pairing — **out of scope** (Android has no pairing UI today; guests and legacy passwords suffice, matching TweetWeb's scope). Recorded in the memo.

## What deliberately does NOT change

`ownerSessionRequired` stays off (no backend change in this port at all — zero backend commits). Reads, `add_tweet`/`delete_tweet`/`update_tweet` positions, `toggle_following` routing (already acting user's root), message_check/fetch routing — untouched. Old-wire-form fallback on old nodes preserved by all capability gates.
